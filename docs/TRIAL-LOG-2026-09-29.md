# Trial log — bringing Qwen3.8 Flash Next back to 3 Sparks (2026-09-28 → 09-29)

Goal: run Qwen3.8 Flash Next NVFP4 across all three Sparks (sparkmain, spark1, spark2/"spark-sep")
the way it ran on 2026-09-02 (TP=3), record every trial and error, try PP=3 and record why it
fails, and keep the speed good.

"Observed" = a command in this session printed it. "Inferred" = my reading, not tested.

## T3 — PP=3 fails (and why)

Recipes: `configs/colonel-qwen3.8-flash-next-nvfp4-pp3.yaml` (MTP 4) and `...-pp3-nospec.yaml`.
TP=1 x PP=3 was chosen because it needs none of the divisibility that TP=3 needs.

Observed, both variants, within ~40 s and before any weights load:

```
NotImplementedError: Qwen4Exp N-gram PLE embedding requires pipeline_parallel_size=1 because
non-first pipeline ranks do not receive the raw input_ids it needs. Please run with PP=1.
```

Raised from `vllm/model_executor/models/config.py` `verify_and_update_config`. The no-speculative-decoding
variant fails identically, so this is not an MTP interaction. The model's N-gram per-layer embedding
needs the raw token ids on every rank, and pipeline stages after the first only receive hidden states.
Fixing it means changing how token ids are passed between pipeline stages in vLLM — a model/engine
change, not a recipe change. Evidence: `results/20260929-pp3-attempt/`.

Not tried: PP=3 on the old image. The old hand-ported model is a different code path and may not carry
this restriction; that was not tested.

## T4 — TP=3 with 4 MTP tokens crashes

Recipe `qwen3.8-next-flash-nvfp4-tp3-mtp4` (already in the launcher) on the old image. Weights loaded,
KV cache allocated (9,171,560 tokens), graphs captured, then during `warmup_kernels`:

```
torch.AcceleratorError: CUDA error: an illegal memory access was encountered
  ... speculator.propose -> _multi_step_decode -> _build_draft_attn_metadata
  -> attn_utils.build_attn_metadata -> flashinfer.py build -> backend.py seq_lens_cpu
```

`dmesg` on all three nodes shows `NVRM: Xid 31` MMU faults; the same fault address
(`0x152_99e11000`, PTE read) appears on all three nodes. Evidence:
`results/20260929-tp3-mtp4-crash/`.

Inferred, not tested: the failure is specific to the multi-step draft path (more than one speculative
token) in combination with the old patched Qwen3-Next MTP model. 1-token MTP does not use that path
and runs cleanly. MTP 2 and 3 were not tried and would likely hit the same path.

## What TP=3 on the new image would take (not attempted)

Observed model dimensions vs 3-way split: attention heads 24 (ok), KV heads 2, experts 512,
MoE intermediate 640, linear-attention key heads 16, vocab 248320 — all not divisible by 3.
The new native attention code raises when the KV head count does not divide the TP size
(`nvidia/qsa.py:217`, `nvidia/b12x_qsa.py:908`; read, not triggered). The old image solved this with a
virtual-TP padding layer touching 22 vLLM files; the new image has none, and the new model
(`models/qwen4_exp`, ~20.7k lines: QSA attention, PLE tables, hyper-connections, n-gram embeddings)
has 14 files that use the TP size. It needs a new plan builder plus hooks in each, and a numerical
check against TP=2 output.

## Incident: spark2's container was removed by mistake

When asked to delete the current Qwen image I removed `vllm_node` and the image on all three nodes.
`sparkmain`'s `CLAUDE.md` then turned out to say spark-sep ran its own solo Qwen and must be left alone;
I had not read it first. That instruction was later withdrawn by the owner and the file updated
(spark-sep is now a free third node). Lesson recorded: read the per-host notes and check what each
node is serving before touching a shared container name.

## Operational notes

- `docker pull` by digest on spark1/spark2 worked; a "pull still running" check I wrote matched its own
  command line — check `docker images`, not `pgrep`, for completion.
- `build-and-copy.sh -c` assumes one SSH username for all nodes; ours differ, so images were pulled per node.
- TP=2 (`qwen.service`) and TP=3 cannot run together (same GPUs, same port 8100). Switch with
  `systemctl stop qwen.service` then the TP=3 boot script, and back with `systemctl restart qwen.service`.
  The stop script only cleans sparkmain and spark1; remove `vllm_node` on spark2 by hand after a TP=3 run.
