## Why a 3rd node is not expected to double anything (inferred from the padding plan and cited profiles)

Per-rank work at TP=3 with padding vs TP=2: Q heads 36/3 = 12 vs 24/2 = 12 (equal), MoE 768/3 = 256 vs 640/2 = 320
(-20%), GDN value heads 54/3 = 18 vs 48/2 = 24 (-25%). Attention work per rank does not fall at all. sglang#36796
profiles 2x Spark TP=2 as kernel-bound (NVFP4 GEMM 34%, grouped MoE 16%, QSA gather 12%, NCCL 7%). The DeepSeek 3-vs-2 work
and the GLM TP=3 handoff reach the same reading: the 3rd node buys memory/KV and long-context speed, not single-stream.

## T3 — PP=3 fails
Recipes `configs/colonel-qwen3.8-flash-next-nvfp4-pp3.yaml` (MTP 4) and `...-pp3-nospec.yaml`. Observed, both, within ~40 s,
before any weights load:

```
NotImplementedError: Qwen4Exp N-gram PLE embedding requires pipeline_parallel_size=1 because
non-first pipeline ranks do not receive the raw input_ids it needs. Please run with PP=1.
```

Raised from `vllm/model_executor/models/config.py` `verify_and_update_config`. Independent of speculative decoding (no-spec
variant identical). The N-gram per-layer embedding needs raw token ids on every rank; later pipeline stages only receive
hidden states. Evidence: `results/20260929-pp3-attempt/`.

**Leads that PP=3 may not be dead (unverified):** vllm issue #54709 (open) proposes checking that all PLE layers sit on
rank 0 and reports a PP4 run; 1Cat-vLLM #479 lists two separate PP gates and a hyper-connection loader fix;
zebgop-ops/qwen38-flashnext-pp reports PP=3 + MTP at 74 tok/s on SM_80 cards; SGLang PR #40501 (merged 2026-09-22) reportedly
adds PP + MTP for Qwen4Exp (our SGLang image is from 09-03 and predates it). Not tested here.

## T6–T8 — SGLang TP=3
Boot: `MAX_TOTAL_TOKENS=600000 ~/3spark-qwen-flash-build/scripts/sglang-flashnext-boot.sh 3` (image
`sglang-flashnext-tp3:local` on all nodes; ~510 s to HTTP 200). `sglang-flashnext-validate.sh`: 6 PASS / 0 FAIL on every boot.
Live args confirmed: `--tp-size 3 --nnodes 3 --speculative-num-steps 3 --speculative-num-draft-tokens 4`.

- **First sweep reported `EXCLUSIVITY_FAIL` (delta 0, 0 foreign requests).** Cause: the sweep script resolves
  `exclusivity.py` next to itself; run from the home directory it picked up an older copy with no SGLang metric mapping
  (0 mentions of `sglang` vs 10 in the current copy). The server's own counter showed exactly 155 streaming requests
  (the sweep's expected count) plus 6 from the validation battery, so the run was exclusive. Re-run from the build
  directory: `EXCLUSIVITY_PASS delta=155 expected=155`. Keep one copy of `exclusivity.py`.
- **`gpu_idle_guard.py` refuses to launch because `dcgm-exporter` is GPU-capable.** The repo's newer boot script uses the
  guard; the copy on sparkmain uses an older inline check that only blocks on `vllm_node`/`sglang_node` or a listener on
  8100. The guard has no allowlist and is deliberately strict, so it was not weakened; the sparkmain script (identical
  serving flags) was used. Decide whether the guard should learn to ignore the monitoring exporter.
- **T8:** `NotImplementedError: Qwen QSA requires speculative_num_draft_tokens <= the QSA compress ratio (4)`
  (`results/20260929-sglang-tp3-C-spec5-failed/`). 3 steps / 4 draft tokens is already the maximum.
- **GSM8K sanity check (150 problems, `scripts/run_gsm8k.py`, 512-token cap, thinking off, temp 0):** 86.0% (129/150). 20 of the 21 failures have no final-answer sentence (responses cut off mid-verification at the 512-token cap); only 1 is a genuinely wrong answer (#142, gold 400, pred 700). Of the 130 responses that finished, 129 were correct (99.2%). This argues against gross corruption from the padded shards, but it is not a numeric gate: no TP=2 reference score was run, and the sample is small. Raw: `results/20260929-sglang-tp3-gsm8k/`.
- **Still owed (from the 09-04 handoff):** the logprob gate, TP=3 vs TP=2 shared-prefix |dlogprob|. Padded shards can serve
  fluent, slightly wrong text that a 6-prompt battery passes; "correct on the battery" is not "numerically gated".
- **Known upstream landmine (lead, sglang#37326, open):** MTP acceptance can decay toward 0 over ~24 h of uptime on
  qwen4_exp; restart fixes it. Watch `sglang:spec_accept_length`; below ~2 means restart.
- **Launched by hand** (`docker run -d`), not under systemd. It will not survive a reboot.

## What TP=3 on the native vLLM stack would take (not attempted)
Model dimensions not divisible by 3: KV heads 2, GDN key heads 16, MoE/shared intermediate 640, vocab 248320. Native code
raises on non-divisible KV heads (`nvidia/qsa.py:217`, `b12x_qsa.py:908`; read, not triggered). Two precedents exist: our old
virtual-TP layer (22 files) and the BHCC2025 load-time padding (2 hooks + a standalone module). Design work on the exact
per-tensor plan and on non-TP decompositions is in `docs/TP3-DIVISIBILITY-PLAN.md` and `docs/NON-TP-DECOMPOSITIONS.md` if present.

## Operational notes
- Check `docker images`, not `pgrep`, for pull completion (my `pgrep -f` matched its own command line).
- `pkill -f <pattern>` inside an SSH command matches the SSH command itself and kills the session.
- `build-and-copy.sh -c` assumes one SSH username for all nodes; ours differ, so images were pulled per node by digest.
- Only one engine at a time: vLLM TP=2 (`qwen.service`), vLLM TP=3, and SGLang TP=3 share the GPUs and port 8100.
  `qwen-service-stop` cleans only sparkmain and spark1; remove `vllm_node`/`sglang_node` on spark2 by hand.
- The first sweep after a boot is a cold lower bound; discard it or run a warm-up sweep first.
